# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repository is

This is the **deployment repo** for Mini Platform, a GitOps Kubernetes reference
stack. It is not an application codebase — there is no service source code to
compile. It holds the environment-specific, first-party half of the stack that
**Argo CD** reconciles:

- `minikube/values/` — **integration overlays**, one `*-values.yaml` per managed
  release, plus a `*-resources.yaml` beside it for each release that owns an
  ingress route or Vault secrets. This is where Mini Platform's customizations
  live. Contains **no credentials**.
- `minikube/gitops/` — the **Argo CD app-of-apps** wiring plus the shared
  `app-resources` chart those `*-resources.yaml` files feed (the only
  first-party Helm charts here).
- `scripts/` — bootstrap, deploy, validate, and port-forward tooling.

`minikube/` is one **environment overlay**. A new environment is a sibling
directory (e.g. `prod/`) reusing the same charts repo.

The **vendored upstream Helm charts** (`charts/`) live in a **separate repo**,
[`mini-platform`](https://github.com/nolimitkun/mini-platform). Treat those as
third-party; they are not linted or modified here. Several scripts expect a
local checkout of that repo as a sibling directory (`../mini-platform`), override
with `--charts-dir` or the `CHARTS_DIR` env var.

## Two-source, multi-source model

Every generated Argo CD `Application` is **multi-source**: source 0 pulls the
chart (from the charts repo for `charts/*` paths, or from this repo for the
first-party `minikube/gitops/*` charts) and the last source is a `ref: deploy`
pointing at this repo so each `valueFiles` entry can be written `$deploy/<path>`
(repo-root-relative, never depending on chart-path depth). This is the reason
the split works at all — a single-source Application cannot mix a chart from one
repo with a values file from another.

An application that declares a `resourcesFile` gets a **second
manifest-producing source** between the two: the shared
`minikube/gitops/app-resources` chart rendered against that file. That is how a
release's ingress route and the `VaultStaticSecret` mappings it consumes are
created, self-healed and pruned **with the release itself** rather than from two
cluster-wide lists.

Two `(repoURL, revision)` pairs therefore drive everything and **must stay in
sync** across files: `chartsRepo`/`chartsRevision` and `deployRepo`/`deployRevision`.
Never hand-edit them in more than one place — run `scripts/set-repo.sh`.

## Two invariants that govern every change

1. **Argo CD reconciles Git commits, never the working tree.** Editing an
   overlay or GitOps chart has no effect until it is committed *and pushed* to
   the branch/revision Argo CD tracks. A clean `git status` (in **both** this
   repo and the charts checkout) is a precondition for the `--local-source`
   deploy path.
2. **No credentials in Git.** Vault is the source of truth for all application
   secrets; Vault Secrets Operator (VSO) materializes Kubernetes Secrets from
   it. Never add a Secret manifest or a literal credential to `minikube/values/`
   or `minikube/gitops/`. New credentials are generated by
   `scripts/bootstrap-vault-secrets.sh` and surfaced by listing their Vault path
   in the consuming release's `minikube/values/<name>-resources.yaml`.

## Validation (run before every commit to GitOps wiring)

```bash
CHARTS_DIR=../mini-platform ./scripts/validate-gitops.sh
```

This is exactly what CI (`.github/workflows/validate.yaml`) runs. It:

- checks every `valuesFile` and `resourcesFile` referenced by the app-of-apps
  exists locally, and that no `minikube/values/*-resources.yaml` is orphaned
  (an unreferenced one renders nothing at all),
- checks every `chartPath` resolves (`charts/*` against `CHARTS_DIR`, skipped if
  that checkout is absent; first-party `minikube/gitops/*` locally),
- `helm lint`s and `helm template`s the app-of-apps chart (passing all four
  source parameters) and the `app-resources` chart once per `resourcesFile`,
- runs `kubeconform` over the rendered manifests,
- `shellcheck`s `scripts/*.sh`,
- runs `gen-catalog.py --check` and `gen-projects.py --check`, so generated files
  can't drift from `catalog/models.yaml` and `projects/*.yaml`,
- runs `opa check --strict` and `opa fmt` on every bundle under `policies/`,
  `opa test` over all of them, then builds each bundle and loads them together
  (their `.manifest` roots must not overlap), and
- runs `promtool` on the rendered Prometheus config and the alert rules.

`helm` is required; `kubeconform`, `shellcheck`, `opa` and `promtool` are
skipped if absent locally but always run in CI. Beyond the Rego unit tests in `policies/`, "tests"
here means rendering and schema-checking.

## Architecture

Default AI request path: `Open WebUI → agentgateway → KServe InferencePool (EPP) → vLLM`.
**agentgateway** is the platform's model and tool gateway (`docs/agentgateway.md`):
one OpenAI-compatible endpoint for every model (self-hosted KServe releases, Gemini on Vertex AI over the
mini-cloud VPN, DeepSeek), passthrough routes to Google's speech APIs, and one MCP
endpoint over the cluster's MCP servers. Every request carries a per-project API key
and is decided by **OPA** (ext_authz, FailClosed) from the Rego in `policies/gateway`
and the per-project data, two bundles in MinIO with disjoint `.manifest` roots, both
signed with a Vault Transit key that never leaves Vault (OPA verifies them). The
**project registry** (`project-registry`, code in `nolimitkun/project-registry`,
docs/project-registry.md) publishes both, every change after policy-decided approvals
(`policies/gateway/portal.rego`): it holds the projects, agents and exceptions as change
requests and publishes `gateway-projects` after replaying recent decisions; and it files
every new commit on `main` as a **policy change** (it runs `opa test`, builds and signs
`gateway-policy`, replays), which goes live, without an Argo CD sync, only once the
platform team and security approve it in the portal. So a Rego change must pass `opa test`
and the two-bundle load (run by `validate-gitops.sh`) to merge, and an approval to reach
OPA; to try a branch on the cluster, point `policy.ref` in the project-registry values at
it for the test. OPA Control Plane was
removed. Each project's rate limits travel with OPA's allow decision (dynamic metadata →
`limitOverride`); the rate-limit config lists no project. `scripts/policy-replay.py` replays recent decisions
from Loki against a change. Models and Google APIs are declared
once in `catalog/models.yaml`; `scripts/gen-catalog.py` generates the gateway chart's
`files/catalog.json` and the policy's `catalog/data.json` from it (CI checks they are
current). API keys belong to projects (data class, placement, allowed models, key ids,
MCP tools). The project registry is where projects, agents and exceptions change now;
`projects/*.yaml` and `agents/*.yaml` are the snapshot it imported, in the same format,
and still the source of what the registry doesn't cover yet: the API keys the Vault
bootstrap creates (it reads the key ids from them) and the agentregistry catalog;
`scripts/registry-export.py` writes the registry's records back to them (by hand,
or daily by the CronJob `project-registry-git-export`, which opens one PR on the
`registry-export` branch with the token in Vault `registry-git`). The registry's
portal is `registry.test/portal/` (Keycloak login with PKCE). The budget
alert is one rule joining spend with the registry's `project_budget_usd`; who may
submit and who must approve a change are both Rego (`portal.may_submit`,
`portal.required_approvals`). `scripts/gen-projects.py` validates that format against
`projects/schema.json` and renders `data.projects` (one file per project under
`policies/gateway-projects`); the registry's publisher runs the same script on its
records, so the two can't disagree on the rules. Agents
(`agents/*.yaml`) belong to a project and narrow it: own keys, models, MCP tools,
owner, autonomy; gen-projects.py adds them to the policy data (`data.agents`,
each project's `agent_keys`) and to agentregistry, and checks a kagent agent is
wired to its own ModelConfig and secret. `catalog/tools.yaml` classes every MCP
tool behind the gateway (read, write, irreversible; unlisted = irreversible) and
OPA holds each agent to its autonomy; `scripts/tools-drift.py` reports tools that
appeared, vanished or changed since they were classified. **agentregistry** is the catalog of
MCP servers and agents; its entries live in `minikube/gitops/agentregistry-catalog`.

Self-hosted models are KServe `LLMInferenceService`s in `model-hprd` /
`model-prod`, created by the model onboarding pipeline (separate repo,
`model-onboarding-pipeline`); this repo's `model-serving` app owns their
namespaces, Vault-fed credentials and the gateway policy that sends the vLLM key.
A catalog entry with `provider: KServe` (`deployment: <ns>/<name>`,
`servedModel`) routes a model name to a release's InferencePool; projects with
`deployments: true` (the pipeline) may call `/<serving ns>/<name>/v1/...`
directly. Weights live in MinIO bucket `models` (object-locked). A
Gateway-wide AgentgatewayPolicy must never read `response.body`: agentgateway
then buffers every response, streaming included.

KServe itself is platform GitOps too: `gateway-api-crds`, `cert-manager`,
`kserve-llmisvc-crd` (wave -4), `lws`, `kserve-llmisvc-resources` (-3) and
`kserve-runtime-configs` (-2), versions as KServe v0.21.0's own installer. The
vendored KServe charts carry v0.21.0-rc1 names (the release published no
others); `kserve.version: v0.21.0` picks the release images. The two apps that
call an earlier wave's webhook set `retry: true`, since waves only order
creation; `kserve-runtime-configs` sets `serverSideDiff: true`, since its CRD's
schema defaults would otherwise leave it OutOfSync. cert-manager's leader
election lives in its own namespace (the project does not deploy to
`kube-system`).

Supporting subsystems: Vault + VSO (secrets), Ingress NGINX (`.test`
hostnames), MLflow (experiments), Qdrant
(vectors), Spark Operator, Superset → Trino (analytics), Keycloak (identity),
MinIO (S3 object store), all reconciled by Argo CD.

**Two agentic-AI consumers sit on top of the stack, both running their model
through agentgateway** with their own API keys: kagent (chat UI, agents, Grafana
MCP) and HolmesGPT (an investigation API surfaced in Open WebUI through a Pipe).
Holmes also sends its native investigation trace directly to its dedicated
Langfuse project over authenticated OTLP/HTTP.

kagent's own spans reach Langfuse as well, by a third route and into a `kagent`
project of their own: Alloy forwards them. A conversation then reads as one
trace — the LLM turns with their prompts and completions, the tool calls with
their arguments and results — rather than as the run of unrelated model calls
the gateway sees. The fan-out is configured in `alloy-values.yaml`, not in
`kagent-values.yaml`; see the tracing block there for why.

Holmes reads Kubernetes over read-only RBAC and reaches Prometheus
directly but dashboards, Loki and Tempo through Grafana. It also reads Helm and
Argo CD deployment state, and uses a hard-allowlisted GitHub MCP server for
repository, pull-request and Actions context. Grafana basic auth comes from
`holmes-grafana`, the same compromise `kagent-grafana` makes, providing clickable
links back into Grafana and keeping
`grafana-values.yaml` the only description of where each backend lives, keyed on
the fixed datasource uids. Its overlay is also the reason `alloy-values.yaml`
carries an `app`-label fallback: the holmes chart labels its pod `app: holmes`
and never sets `app.kubernetes.io/instance`, which is what Alloy reads first,
so without the fallback its logs would arrive with an empty `app` label.
Helm release state is stored in Secrets, so the second-source resources chart
binds a namespace-scoped `holmes-helm-release-reader` Role; never widen that
permission to a ClusterRole.

**Observability is three signals behind one Grafana.** Prometheus scrapes
metrics; Grafana Alloy (a DaemonSet, Promtail's successor) tails pod logs
through the Kubernetes API into Loki; agentgateway, kagent and the other OTLP
producers push spans through Alloy into Tempo. All three backends are cluster-internal — Grafana is
the only UI, and its provisioned data sources carry fixed uids (`prometheus`,
`loki`, `tempo`) precisely so the cross-links between them can reference each
other by name: Loki `derivedFields` → Tempo, Tempo `tracesToLogsV2` → Loki,
Tempo `serviceMap` → Prometheus. Changing a uid breaks those links, and —
because `persistence.enabled` keeps the old datasource row — needs a matching
`deleteDatasources` entry. Two coupling points worth knowing: the trace→logs
jump matches the span's `service.name` against Loki's `app` label, which Alloy
derives from `app.kubernetes.io/instance` (agentgateway's proxy reports
`agentgateway-proxy`, its instance label);
and Tempo's metrics generator remote-writes span metrics into Prometheus, which
is why the Prometheus overlay must keep `--web.enable-remote-write-receiver`.
Loki and Tempo both run single-binary against a filesystem PVC — neither is
sized for real volume, and the vendored `tempo` chart is deprecated upstream in
favour of `tempo-distributed` (kept deliberately; see `tempo-values.yaml`).

**GPU metrics come from dcgm-exporter, and how it reaches the card is the one
surprising thing about it.** It requests no `nvidia.com/gpu` — the node has
exactly one and vLLM holds it — so nothing injects the driver the way the
device plugin does for vLLM. Upstream expects `runtimeClassName: nvidia` or
CDI; this node has neither, and a pod that asks for nothing NVIDIA-shaped sees
no `/dev/nvidia*` at all. What reaches it instead is the container toolkit's
prestart hook, which fires on `NVIDIA_VISIBLE_DEVICES` and bind-mounts devices
and driver libraries in. The upstream image already sets that variable, so the
overlay's copy is deliberate restatement rather than the thing making it work;
the `NVIDIA_DRIVER_CAPABILITIES: utility` beside it *is* a real change, dropping
`compute` from what the image asks for. Because the exporter exits 1 rather than
degrading when no GPU is present, its app-of-apps entry carries an `enabled`
toggle — set it false for a CPU-only cluster, or its wave `-1` Application never
goes Healthy and stalls every later wave.
Its scrape job sets `honor_labels` on purpose: the exporter reads the kubelet
pod-resources socket, so its `pod`/`namespace`/`container` labels name the
workload *holding* the GPU (today vLLM), which is what makes `DCGM_FI_*`
joinable with vLLM's own series. The chart's ServiceMonitor stays off — there
is no Prometheus operator here, so `monitoring.coreos.com` does not exist.

**Grafana dashboards are first-party files, and they do not go in the chart.**
They live in `minikube/gitops/app-resources/dashboards/*.json`, are listed by
name in `grafana-resources.yaml`, and render as ConfigMaps labelled
`grafana_dashboard: "1"` that Grafana's dashboard sidecar collects. To add one,
drop the JSON in that directory and add its name to that list — nothing else.
The tempting alternative, the grafana chart's own `dashboards` value with a
`file:` key, resolves against the **chart** directory, so it only works for
dashboards committed inside the vendored chart, where the next upstream bump
deletes them (subtrees are replaced verbatim). Four dashboards used to live
there for exactly that reason. Note also that enabling any Grafana sidecar
makes the chart grant its ServiceAccount read on ConfigMaps *and Secrets*, with
a **ClusterRole** by default; `rbac.namespaced: true` in the overlay keeps that
a namespace-scoped Role, and should stay.

Tempo is the default destination for traces but not the only one: Alloy also
copies kagent's spans to Langfuse, into the `kagent` project the
`langfuse-kagent-project` release provisions. The selector is kagent's own
`service.namespace` resource attribute (`mini_platform`), which nothing else on
this platform sets, and the A2A transport's spans are dropped on the way — two
thirds of a conversation, one per queued event, carrying no attributes. Tempo
still receives everything, so nothing about the existing cross-links changes.
Any producer that starts setting `service.namespace` would silently join that
feed.

**Keycloak is the identity provider for every browser-facing service.** The
`mini-platform` realm — clients, the two realm roles, the two groups, and two
seed users — is declared inline in `minikube/values/keycloak-values.yaml` under
`keycloakConfigCli.configuration` and imported by a post-sync Job, so it is
re-applied on every Argo CD sync and console edits are reverted. Client secrets
live in the single Vault secret `keycloak-sso`: keycloak-config-cli reads the
whole thing with `envFrom` and interpolates `$(env:NAME)` into the realm, while
each component mounts only its own key. **The key names in that realm and in
`bootstrap-vault-secrets.sh` must match** — an unresolved variable is imported
literally, producing a client secret nothing can authenticate with.

The design turns on **one issuer URL, `http://keycloak.test`, for browsers and
pods alike**: `deploy-minikube.sh` adds a CoreDNS rewrite so `keycloak.test`
resolves in-cluster, and `KC_HOSTNAME` pins what Keycloak stamps into `iss`.
Splitting frontchannel and backchannel hostnames is not an option — Argo CD,
oauth2-proxy and Langfuse all validate the issuer, and none of them accept a
separate internal URL. The cost is that Keycloak's admin console is unreachable
over a port-forward.

Seven components speak OIDC natively (Grafana, Open WebUI, Superset,
JupyterHub, Argo CD, MinIO, Langfuse). Four cannot and sit behind a shared
**oauth2-proxy** as ingress-nginx forward-auth: MLflow, kagent, agentregistry,
and agentgateway's admin UI (admins only, through the route's `allowedGroups`).
HolmesGPT and the agentgateway API are outside the scheme altogether: no browser UI, so
they authenticate their own requests (`HOLMES_API_KEY`, per-project gateway API
keys) and their routes are left unprotected. A route opts in with `protectedPaths` in its own
`minikube/values/<name>-resources.yaml`, which renders a second Ingress
carrying the auth annotations plus an unauthenticated `/oauth2` Ingress; the
split matters because nginx applies those annotations to every path in an
Ingress, and a protected `/oauth2/start` would loop. **Any path whose clients
authenticate themselves must be exempted** — the gateway's API and MLflow's
`/api` both are (via `openPaths`, or by not being listed at all), because an
SDK or CLI sending its own credentials cannot follow an interactive SSO
redirect and just receives a 302. Local break-glass logins
are kept everywhere they exist — Superset is the sole exception, since
Flask-AppBuilder has a single `AUTH_TYPE`. Argo CD is the one consumer outside
the `mini-platform` namespace, so `keycloak-resources.yaml` renders it a
`VaultStaticSecret`, `VaultAuth` and ServiceAccount in `argocd`, and the Vault
Kubernetes auth role binds that namespace too. That mapping sits with Keycloak
rather than with Argo CD because Argo CD syncs in wave `-5`, before VSO
installs the `VaultStaticSecret` CRD — a failed resource there would stall the
root sync ahead of the operator that defines the type.

**Vault must be initialized and unsealed before dependent apps go healthy.**
Early Argo CD syncs intentionally show missing-secret failures until Vault is
seeded and the `VaultStaticSecret` resources synchronize — this is expected, not
a bug.

### The app-of-apps and sync waves

`minikube/gitops/root-application.yaml` is the single root Argo CD `Application`.
Its `source` points at this repo's app-of-apps chart
(`minikube/gitops/mini-platform/`) and passes four helm parameters
(`chartsRepo`, `chartsRevision`, `deployRepo`, `deployRevision`). That chart's
`templates/applications.yaml` loops over the `applications:` map in
`minikube/gitops/mini-platform/values.yaml` to emit one multi-source Argo CD
`Application` per release.

Each entry maps a `chartPath` (under `charts/` in the charts repo, or
`minikube/gitops/` here) to a `valuesFile` (under `minikube/`), an optional
`resourcesFile` (the second source), and a **sync wave** that orders rollout:

| Wave | Tier |
| --- | --- |
| `-5` | Argo CD |
| `-4` | Vault, VSO, kagent CRDs |
| `-4` (also) | agentgateway CRDs, Gateway API CRDs, cert-manager, KServe's CRDs |
| `-3` | Stateful deps (postgres, redis, qdrant, spark-operator), LWS, KServe's controller (`kserve-llmisvc-resources`) |
| `-2` | Keycloak, Langfuse, MLflow, Trino, KServe's presets (`kserve-runtime-configs`) |
| `-1` → `0` | MinIO, Prometheus, dcgm-exporter, Loki, Tempo, Langfuse's project jobs, then Grafana, Alloy, JupyterHub, Superset, the agentgateway controller and OPA (`opa-policy`), the model serving namespaces (`model-serving`), the PostgreSQL of agentregistry and of the project registry |
| `1` → `2` | agentgateway's Gateway/models/policies (`agentgateway-config`), the rate-limit service, the semantic router, the project registry and agentregistry, then Open WebUI, kagent, HolmesGPT, oauth2-proxy and the agentregistry catalog |
| `3` | Open WebUI Holmes Pipe, after Holmes and its API-key mapping are healthy |

All generated Applications use `automated` sync with `prune: true`,
`selfHeal: true`, `CreateNamespace=true`, and `ServerSideApply=true`.

**A secret is declared on the earliest-syncing application that consumes it.**
A pod cannot go Ready without a Secret it mounts, and Argo CD holds each wave
until the previous one is healthy, so a secret first needed in wave `-1` but
declared on an application in wave `1` deadlocks the rollout. Placements that
follow from that rule rather than from ownership are commented as such: the OPA
bundle accounts (`opa-bundles-writer`, `opa-bundles-reader`) are declared on
MinIO (wave `-1`), which creates them, rather than on `opa-policy`; and MinIO
sits well after the stateful tier it would otherwise belong to because its
console login needs `keycloak-sso`.

MinIO shows the same rule applying to a **running** dependency rather than a
Secret, which is why it is a wave later still, at `-1`. It resolves its OIDC
discovery URL once during startup and, if that fails, serves on without a
provider — the console falls back to username/password with no SSO button and
never recovers without a restart. Sharing Keycloak's wave was enough to lose
that race every time, since MinIO is serving within seconds and Keycloak has a
database and a realm import ahead of it. MLflow and Langfuse each ship their own MinIO subchart; the only consumers of
this one are the bundle builders and OPA (`opa-policy`, `project-registry`, wave `0`–`1`), so the later wave costs
nothing.
The wave only orders the initial rollout, though; a container that restarts
later can lose the lookup to any transient, which is why the deploy script ends
with `ensure_minio_sso` — it asks the console which login strategy it is
offering and restarts MinIO if the answer is `form`.

The rule goes one step further for **PreSync hooks**, which Argo CD runs before
every regular resource in the same Application — sync waves order the sync
phase, they cannot put a resource ahead of a hook. A secret a hook mounts must
therefore come from an *earlier application*, never from the one being synced,
or the hook waits on a Secret that waits on the hook. (No release has such a
hook today; LiteLLM's schema migration was the one case.) Ingresses have no such
constraint —
they are healthy the moment they are applied — so a protected route rendered
before oauth2-proxy exists simply answers 503 until wave `2`.

### Secret flow

`scripts/bootstrap-vault-secrets.sh` writes random credentials into the Vault
KV mount `mini-platform/`. Each release's
`minikube/values/<name>-resources.yaml` lists the secret *names* it needs under
`vaultSecrets`; the `app-resources` template renders a `VaultStaticSecret` per
name that VSO syncs into a like-named Kubernetes Secret. The two must agree: a
secret a workload needs must be **both** written by the bootstrap script **and**
listed in some release's resources file. Langfuse's headless init creates only
the org and its owner account; each consumer has a project of its own. Holmes: `holmes-langfuse-project` is mounted only by the
`minikube/gitops/langfuse-project` provisioning job, while Holmes itself mounts
the derived exporter header from `holmes-langfuse`. Open WebUI follows the same
split. kagent's `kagent-langfuse-project` has no runtime mirror, because kagent
exports nothing itself — Alloy does, and mounts the provisioning pair as it
stands.

## Common conventions / recipes

**Adding or changing a managed component:** edit the matching
`minikube/values/*.yaml` overlay (not the vendored chart — that lives in the
charts repo). To add a *new* release: add the upstream chart under `charts/` in
the **charts repo**, add an overlay under `minikube/values/`, add an
`applications:` entry in `minikube/gitops/mini-platform/values.yaml` with an
appropriate `wave` (`chartPath: charts/<name>`,
`valuesFile: minikube/values/<name>-values.yaml`). If it needs credentials or a
browser route, add `resourcesFile: minikube/values/<name>-resources.yaml` and
create that file: `vaultSecrets` for each Vault path (also add it to
`bootstrap-vault-secrets.sh`), `routes` for the `.test` hostname. Put it behind
Keycloak while you are there, either as a realm client (see the SSO notes above)
or, if it has no OIDC support, with `protectedPaths` on that route.

**Pointing at forks/branches:** the two source URLs/revisions appear in several
files that must stay in sync. Never hand-edit them — run:

```bash
./scripts/set-repo.sh \
  --charts-repo-url https://github.com/<owner>/mini-platform.git --charts-revision <branch> \
  --deploy-repo-url https://github.com/<owner>/mini-platform-deployment.git --deploy-revision <branch>
```

It rewrites `minikube/gitops/root-application.yaml`,
`minikube/gitops/mini-platform/values.yaml`, and the `scripts/deploy-minikube.sh`
defaults together. Any subset of the four values may be passed.

**Deploying / bootstrapping:** `scripts/deploy-minikube.sh` automates the full
Minikube + Argo CD + Vault bring-up (key flags: `--reset`, `--local-source`,
`--no-gpu`, `--rotate-secrets`, `--charts-dir`). It uses the local charts
checkout only to bootstrap Argo CD itself and, in `--local-source` mode, to
serve **both** repos through an in-cluster git daemon. The self-hosted models (KServe releases)
need an NVIDIA GPU — for CPU-only work pass `--no-gpu`. `scripts/port-forward-services.sh` exposes
services on the Minikube host (`--mode lan` for LAN access).

The README is the authoritative deployment/operations reference and includes the
full manual bootstrap, service endpoints, and credential-retrieval commands.
Consult it before changing deploy/bootstrap behavior.

## Notes

- This is a **local reference stack**, not production: in-cluster TLS is off,
  Vault uses manual single-key unseal, and Trino/Prometheus/databases/vLLM are
  cluster-internal with no auth. Don't assume hardening that isn't there.
- `tools/` holds what is applied by hand, outside the GitOps reconciliation:
  an optional utility workload (`net-tools.yaml`) and
  `99-rootless-k8s-netlink.conf`, a host sysctl drop-in that
  `scripts/deploy-minikube.sh` refuses to deploy without under rootless Docker
  on Linux. Rootless Docker cannot raise a netlink send buffer from inside the
  node, and kube-proxy's nftables proxier needs a bigger one than the default
  to push this platform's ~120 Services in a single batch. The file explains
  the rest.
- `.github/workflows/validate.yaml` is the CI gate.
